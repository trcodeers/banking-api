# Banking API

A RESTful banking API built with **FastAPI, SQLAlchemy, SQLite, and uv**. It supports account creation, credit and debit transactions, transaction history with pagination, and atomic money transfers between accounts.

## Features

- Create and retrieve bank accounts.
- Credit and debit account balances.
- Validate transaction types, amounts, account IDs, and reference IDs.
- Prevent duplicate transaction references for the same account.
- Reject debits when the account has insufficient funds.
- Maintain transaction history with pagination.
- Transfer money between accounts atomically.
- Enforce database constraints, including foreign keys and non-negative balances.
- Automatically generate interactive API documentation.
- Include automated tests for transaction and transfer rollback scenarios.

## Tech Stack

- **Python 3.13+**
- **FastAPI** — REST API framework
- **SQLAlchemy** — ORM and database operations
- **SQLite** — relational database
- **Pydantic** — request validation
- **uv** — dependency and project management
- **pytest and HTTPX** — testing dependencies

## Installation and Setup

Clone the repository and enter the project directory:

```bash
git clone <your-repository-url>
cd banking-api
```

Install the project dependencies:

```bash
uv sync
```

If your project does not yet declare all dependencies in `pyproject.toml`, install them with:

```bash
uv add fastapi "uvicorn[standard]" sqlalchemy
uv add --dev pytest httpx
```

## Run the Application

Start the development server:

```bash
uv run uvicorn app.main:app --reload
```

The API will be available at:

- **API base URL:** http://127.0.0.1:8000
- **Interactive Swagger documentation:** http://127.0.0.1:8000/docs
- **ReDoc documentation:** http://127.0.0.1:8000/redoc
- **Health check:** http://127.0.0.1:8000/health

The application creates missing database tables during startup. For an existing database, `create_all()` does not migrate previously created tables.

## API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/health` | Check API health |
| `POST` | `/accounts` | Create an account |
| `GET` | `/accounts/{account_id}` | Retrieve an account |
| `POST` | `/accounts/{account_id}/transactions` | Create a credit or debit transaction |
| `GET` | `/accounts/{account_id}/transactions` | Retrieve transaction history |
| `POST` | `/transfers` | Transfer money between accounts |

### 1. Create an Account

**Request**

```http
POST /accounts
Content-Type: application/json
```

```json
{
  "name": "Alice"
}
```

**Example response — `201 Created`**

```json
{
  "id": 1,
  "name": "Alice",
  "balance": "0.00"
}
```

The account ID is generated by the database and should be used in subsequent requests.

### 2. Retrieve an Account

```http
GET /accounts/1
```

Returns the account ID, name, and current balance.

### 3. Create a Credit Transaction

```http
POST /accounts/1/transactions
Content-Type: application/json
```

```json
{
  "type": "credit",
  "amount": "1000.00",
  "reference_id": "TXN-001"
}
```

A successful transaction increases the account balance and records the transaction.

### 4. Create a Debit Transaction

```http
POST /accounts/1/transactions
Content-Type: application/json
```

```json
{
  "type": "debit",
  "amount": "250.00",
  "reference_id": "TXN-002"
}
```

A debit succeeds only when the account has sufficient funds.

### 5. Retrieve Transaction History

```http
GET /accounts/1/transactions?page=1&page_size=10
```

Query parameters:

- `page`: Page number, starting at 1.
- `page_size`: Number of transactions per page, from 1 to 100.

**Example response**

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "page_size": 10
}
```

The `items` array contains transaction records matching the requested page.

### 6. Transfer Money

```http
POST /transfers
Content-Type: application/json
```

```json
{
  "source_account_id": 1,
  "destination_account_id": 2,
  "amount": "150.00",
  "reference_id": "TRANSFER-001"
}
```

**Example response**

```json
{
  "message": "Transfer successful",
  "source_balance": "850.00",
  "destination_balance": "150.00"
}
```

The example assumes the source account initially has a balance of `1000.00` and the destination account has a balance of `0.00`.

Both accounts must exist, the source must have sufficient funds, and the accounts must be different. The transfer records a debit for the source and a credit for the destination.

## Validation and Error Handling

The API uses Pydantic request schemas and database constraints to validate inputs and preserve data integrity.

| HTTP status | Meaning |
|---|---|
| `201 Created` | Account or transaction created successfully |
| `200 OK` | Request completed successfully |
| `404 Not Found` | Account does not exist |
| `409 Conflict` | Duplicate transaction reference or database constraint conflict |
| `400 Bad Request` | Insufficient funds |
| `422 Unprocessable Entity` | Invalid request body, amount, transaction type, or pagination parameters |
| `500 Internal Server Error` | Unexpected account creation failure |

Invalid JSON and missing or incorrectly typed required fields are also handled by FastAPI's request validation.

## Atomicity and Data Integrity

### Transactions

Creating a transaction and updating the account balance occur within a single database transaction. If either operation fails, the database transaction is rolled back so the balance change and transaction record are not partially persisted.

### Money Transfers

A transfer updates both account balances and creates the corresponding debit and credit records within one database transaction. If any operation fails, the entire transfer is rolled back.

### Database Constraints

The database defines constraints for:

- Valid transaction types (`credit` or `debit`).
- Positive transaction amounts.
- Non-negative account balances.
- Valid account references through foreign keys.
- Unique `(account_id, reference_id)` combinations.

SQLite foreign-key enforcement is explicitly enabled in the database configuration.

## Run Tests

Run the automated tests with:

```bash
uv run python -m pytest -v
```

The atomicity tests simulate failures during transaction-record creation and verify that the affected account balances and transaction records are rolled back.

## Assumptions and Design Decisions

1. **Currency:** Amounts are represented as decimal rupee values, with a maximum of two decimal places.
2. **Initial balance:** New accounts start with a balance of `0.00`.
3. **Transaction types:** Only `credit` and `debit` are supported.
4. **Reference IDs:** A reference ID must be non-empty and unique within an account. The same reference ID may be used for a different account.
5. **Transfers:** A transfer creates one debit record and one credit record, using the same reference ID for the respective accounts.
6. **Insufficient funds:** A debit or transfer is rejected if the source account does not have enough money.
7. **Account IDs:** Account IDs are generated by the database; clients provide them when referencing existing accounts.
8. **Authentication:** Authentication and authorization are outside the current assessment scope.
9. **Persistence:** SQLite is used for local development and assessment purposes.
10. **Schema initialization:** The application creates missing tables at startup; schema migrations are not implemented.

## Scope and Limitations

This implementation is intended for a technical assessment rather than production banking use. Before production deployment, additional work would be needed for authentication, authorization, stronger concurrent transaction handling, audit logging, database migrations, operational monitoring, and production-grade database configuration.
